# imboyadmin 自动化测试循环规程

> 供 `/loop` 反复调用。**每轮 = 主块（阶段一/二）+ 三态例行（§3），做完写回文件就退出。**
> 状态全部存在各 md 的「计划变化」列里，不依赖上下文记忆。

调用方式：

```
/loop 20m 按 imboyadmin/tests/auto_test/LOOP_PROMPT.md 执行一轮
```

---

## 0. 每轮开场：先定位自己在哪个阶段

在 `imboyadmin/` 目录下执行：

```bash
grep -rh '^| ' tests/auto_test/*/*.md | grep -v '^| 计划变化' | awk -F'|' '{gsub(/ /,"",$2);print $2}' | sort | uniq -c
```

按结果决定本轮主块做什么：

| 条件 | 阶段 | 动作 |
|---|---|---|
| 还有 `待首测` | **阶段一：测试** | 走 §1 |
| 无 `待首测`，还有 `待修复` | **阶段二：修复** | 走 §2 |
| 两者都为 0 | 主块无可用 | 主块跳过，直接做 §3 |

**每轮无论主块是什么，都必须完成 §3 三态例行（待复验/回归复测/阻塞各处理一条）。**
`待首测` 和 `待修复` 清零后，三态例行就是每轮的全部内容。

## 1. 阶段一：测试（只测不修，绝不改代码）

### 1.1 选取本轮目标

按 `tests/auto_test/` 目录字典序，找**第一个仍含 `待首测` 行的 md 文件**，本轮只做这一个文件。

一次一个页面。不要贪多——上下文越长越容易误判。

### 1.2 环境前置校验（每轮都要做，不要假设）

```bash
# 1. 后端可达（dev server 通过 vite proxy 或直连后端 API）
curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8082/login   # 视实际端口调整

# 2. 前端 dev server 在线（dev server 跑的就是当前工作区代码，无需构建等待）
pgrep -f 'vite' >/dev/null || bun run dev &
```

确认：
- 后端 API 在线（登录接口可拿到验证码图片）。
- 管理员凭据来自 `.env.e2e`：`IMBOY_ADMIN_E2E_ACCOUNT` / `IMBOY_ADMIN_E2E_PASSWORD`，
  固定测试验证码 `1234`（见 `tests/e2e/support/adminAuth.ts`）。
- 若测的是生产构建（`bun run preview` / 线上环境），必须确认构建/部署时间
  **不早于** `git log -1 --format=%ad`，否则测的是旧代码。

### 1.3 逐个功能点验证

对该文件里每一条 `待首测` 行：

**操作前**：打开浏览器 DevTools Network 面板（或 Playwright 的 `page.on('response')`）准备抓包。

**操作**：用浏览器自动化（Playwright / 浏览器 MCP）导航到该页面并执行该功能点描述的操作。
登录统一走 `loginAsAdmin` 的等价流程（账号/密码/验证码 1234）。

**判据，按优先级：**

1. **网络响应是主判据**
   **写操作类（封禁/解封/审核/保存配置/删除/导出）必须看到对应 API 返回 2xx 才算通过。**
   UI 变了不算数——那可能是乐观更新，失败后画面和「什么都没发生」一模一样。
   同时确认 TanStack Query 失效刷新：操作成功后列表应重新拉取（能看到对应 GET 请求）。

2. **DOM 判结构**：该有的按钮/入口在不在；表格列是否完整；空态/错误态是否按设计渲染。

3. **截图判视觉**：布局溢出、暗色/亮色主题、图片渲染、浮层（Dialog/Drawer）遮挡、断词换行。
   - **toast 必须在操作后 1 秒内截图**，晚了必把「有反馈」误判成「静默失败」
   - Radix Dialog/Drawer 打开时必须截图确认遮罩与焦点圈定
   - 控制台报错（console error / unhandled rejection）一律视为疑点，写入备注

### 1.4 必须跳过的情况（标注原因，不要硬试）

- 会打扰真实用户：给真实用户发通知/消息、真实渠道推送
- 会写生产资金数据：人工调整钱包、审核提现、退款
- 不可逆：删除管理员、删除审计日志、注销申请强制通过
- 缺外部条件：需特定权限角色、需大规模数据、需后端未发布的接口

遇到这类：该行改为 `计划变化=阻塞`，`计划时间` 写清楚**需要什么条件才能测**。

### 1.5 立即回写（每验完一个功能点就写，不要攒到最后）

**只覆盖现有行，绝不新增行。**

| 结果 | 计划变化 | 计划时间 | 测试状态 | 测试轮次 | bug 三列 | 备注 |
|---|---|---|---|---|---|---|
| 通过 | `无待办` | `-` | `已通过` | `批次N` | 不变 | 清空 |
| 发现问题 | `待修复` | 当天日期 | `有BUG待修` | `批次N` | 发现+1、待处理+1 | 现象一句话，30 字内 |
| 条件不具备 | `阻塞` | 解阻塞条件 | `未测` | `批次N` | 不变 | 缺什么 |

恒等式必须始终成立：**待处理 = 发现 − 解决**。

### 1.6 本轮收尾

该文件所有 `待首测` 处理完即停止。

**收尾前必须做两件事，缺一不可：**

```bash
# 1. 重生成 README 的汇总与模块索引（否则统计陈旧）
python3 tests/auto_test/regen_readme.py

# 2. 校验 bug 三列恒等式（脚本会自己报错，也可单独跑）
grep -rh '^| ' tests/auto_test/*/*.md | grep -v '^| 计划变化' \
  | awk -F'|' '{gsub(/ /,"",$8);gsub(/ /,"",$9);gsub(/ /,"",$10);
      if($8~/^[0-9]+$/ && $8-$9!=$10) c++} END{print "违反行数: " c+0}'
```

`regen_readme.py` 在恒等式不成立时会以非零码退出——**退出即说明有行写错了，
必须查出来改对，不要绕过**。

然后输出：

- 测了几个功能点，通过几个、发现几个 bug、跳过几个
- 每个新 bug 一句话（页面 + 现象 + 网络响应/控制台关键证据）

**阶段一绝不改任何代码。** 发现的 bug 只记录，留到阶段二。

## 2. 阶段二：修复

前提：全部 `待首测` 已清零。

### 2.1 选取

按目录字典序找第一个含 `待修复` 行的 md 文件，本轮处理该文件里的全部 `待修复` 项。

### 2.2 定位根因（这一步最容易出错，慢一点）

- **改之前先 grep 所有调用点。** 同一根因常常影响多处——在共享组件（`components/shared/*`）
  或 hook 上加一个守卫，比在每个页面各加一遍的 diff 更小，也不会漏掉兄弟调用点
- **不要靠猜改代码。** 假设未被证据证实前，一律在输出里标明「这是假设」
- 区分前端 bug 与后端 bug：API 返回错的去 `imboy/` 后端仓提 issue 或记录 `阻塞=待后端修复`，
  不要在前端打补丁掩盖

### 2.3 改完先跑单测与静态检查

```bash
bun test                          # 单元测试（vitest 风格，bun 跑）
bun run typecheck                 # tsc --noEmit
bun run lint                      # eslint
```

### 2.4 浏览器复验

该文件全部改完后，在 dev server（热更新已生效）逐项复验；涉及路由/构建的改动
再补一次对应 e2e：

```bash
bun run test:e2e --grep '<相关关键字>'
```

复验回写：

| 结果 | 计划变化 | 测试状态 | bug 三列 | 备注 |
|---|---|---|---|---|
| 复验通过 | `无待办` | `已通过` | 解决+1、待处理−1 | 清空 |
| 复验不过 | `待修复` | `有BUG待修` | 不变 | 写清楚**哪一步没过** |

### 2.5 收尾（与阶段一同样强制）

```bash
python3 tests/auto_test/regen_readme.py
```

### 2.6 提交

```
fix(<模块>): <一句话>

<现象>
<根因>
<修法>
<验证：单测/typecheck 结果 + 浏览器复验结果>
```

注意：本仓有 `lefthook`，钩子失败会**静默吞掉 commit**，提交后必须
`git log --oneline -1` 确认真的提交上了。用 `-F 消息文件` 而非 `-m`。

**不要推送。** 推送是外向操作，等人工确认。

## 3. 每轮例行：三态各处理一条（待复验 / 回归复测 / 阻塞）

无论主块是阶段一还是阶段二，**每轮都要从这三个状态各挑一条处理**。
`待首测` 与 `待修复` 清零后，本节就是每轮的全部内容——靠它把回归复测
和阻塞逐步消化掉。

### 3.1 选取（各取全量列表的**最后一条**）

```bash
# 确定性选取（带文件名:行号排序；macOS 上 grep -rh 管道输出顺序不稳定，勿用）
grep -rn '^| 阻塞' tests/auto_test/*/*.md | LC_ALL=C sort | tail -1
# 待复验 / 回归复测 同理，换状态词各跑一次
```

- **为什么取最后一条而不是第一条**：阻塞可能积累很多条，每轮从头取会永远卡在同一条上；
  取最后一条，多轮跑下来自然从尾部向头部全覆盖
- 三个状态各跑一次上面的命令，各得一条；若某状态为 0 条则本轮跳过该状态
- **跳过刚评估过的行**：若取出的行上一轮刚评估过且维持（未产生状态流转），
  依次改取倒数第 2、3… 条，直到取到本轮尚未评估的行；
  §1.4 永久跳过类阻塞行（资金/不可逆/打扰用户）不得霸占选取位

### 3.2 复验前置：改动是否已在运行环境生效（先做，不满足就不测）

- dev server 场景：vite 热更新即时生效，直接测
- 生产/preview 场景：确认构建或部署时间晚于修复提交时间；
  **修复提交晚于部署时间 = 修复不在当前环境里，测不出结果**，不要硬测
- 此时：`计划变化` 改为 `阻塞`，`计划时间` 写 `待重新部署`，测试状态不变，
  bug 三列不变——等部署后下轮从阻塞里把它捞回来

### 3.3 待复验：浏览器复验

按 §1.3 判据执行该功能点。回写：

| 结果 | 计划变化 | 测试状态 | bug 三列 | 备注 |
|---|---|---|---|---|
| 复验通过 | `无待办` | `已通过` | 解决+1、待处理−1 | 清空 |
| 复验不过 | `待修复` | `有BUG待修` | 不变 | 写清楚哪一步没过、网络/控制台证据 |

### 3.4 回归复测：补单独验证历史功能点

挑出的行是「页面整体标过通过、但这个功能点当初没被单独验证」的历史点，
本轮补上单独验证（判据同 §1.3）。与 `待首测` 的区别：待首测=整页从没进过
测试轮；回归复测=同页其他点测过、该点被带过。回写：

| 结果 | 计划变化 | 测试状态 | bug 三列 | 备注 |
|---|---|---|---|---|
| 复测通过 | `无待办` | `已通过` | 不变 | 清空，测试轮次改当前批次 |
| 发现回归 | `待修复` | `有BUG待修` | 发现+1、待处理+1 | 现象一句话 + 网络/控制台证据 |

### 3.5 阻塞：只评估解阻塞条件，不硬试

阻塞是「缺条件测不了」，**不要硬试**（条件真缺时测了也是噪音）。按备注里的
`计划时间`（即解阻塞条件）逐类检查：

| 阻塞类型 | 检查什么 | 条件满足后 |
|---|---|---|
| `待后端发布` | 后端 API 是否已发布（查 imboy 仓 git log / 接口行为实测） | 转 `待复验`，测试状态 `待重验` |
| `待重新部署` | 前端构建/部署时间是否晚于修复提交 | 转 `待复验`，测试状态 `待重验` |
| `待产品决策` | 人工决策是否已定（查 git log / 对话，不要替用户拍板） | 已定=转 `待复验`；未定=维持 |
| `缺外部条件` | 条件是否已具备（权限角色/测试数据/第三方凭据） | 已具备=转 `待复验`；仍缺=维持 |
| 其余 | — | 维持 `阻塞`，本轮不改动 |

**维持不改动的行，只在本轮输出里说「检查过，条件仍缺」，不碰表格。**

### 3.6 三态例行收尾（同样强制）

三态处理完、主块收尾后，统一执行：

```bash
python3 tests/auto_test/regen_readme.py   # 恒等式不成立会非零退出，查错改对，不要绕过
```

并校验恒等式（§1.6 的 awk 命令）。

### 3.7 提交

三态例行改动的是测试计划文档（md），同样要提交，用 pathspec 精确提交本次
动过的文件（**不要无 pathspec 的 commit**，会打包并发会话 staged 文件）：

```
docs: 测试计划更新（批次N：<待复验1条结果>/<回归复测1条结果>/<阻塞1条评估>）
```

## 4. 每轮都要遵守的铁律

1. **只信 `git status --porcelain`**，不信自己「我改了什么」的记忆
2. **判定要有证据**。写「通过」必须有网络 2xx 响应、截图或 console 无报错支撑，
   不能靠「看起来对」
3. **判断运行时状态要问运行时**（浏览器、Network、console），不要用静态读代码代替实测
4. **发现自己此前判断错了，直接更正并说明**，不要藏
5. **绝不新增表格行**，只覆盖。行数增长 = 文档失控
6. **本轮范围外的事不做**：不重构、不优化、不顺手改别的

## 5. 种子文档的生成与扩页

- 首次建立计划 / 新增页面上种子：跑 `python3 tests/auto_test/gen_seed.py`
  （只补不存在的 md，绝不覆盖已有文件），然后跑 `regen_readme.py`
- 种子行是从源码结构（DataTable / FilterBar / useMutation / navigate / toast）抽取的
  **初稿**，首次测该页面时允许把不准确的「功能介绍」改写准确（仍是一行一个功能点，
  不改行数）；发现种子漏了真实功能点时，允许在该页面首测轮一次性补行并在备注写 `种子补录`
